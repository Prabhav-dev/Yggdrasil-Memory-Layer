# Yggdrasil Memory Layer
## System Design

**Status:** A working exact-text MVP is implemented in this standalone project. Semantic embeddings, summaries, retention policy, deletion, and authenticated client transport remain out of scope.

## 1. Purpose

Yggdrasil Memory Layer is a model-agnostic memory service for agents that need durable recall without treating every prior conversation or source file as equally relevant. It separates **retrieval policy** from **durable storage** and preserves a distinct path for information that must remain exact.

The design has two fidelity paths:

- **Semantic memories:** conversational facts and summaries may be condensed and retrieved approximately. A future embedding provider can support similarity search; neither repository currently supplies embeddings or an ANN index.
- **Exact memories:** source code and structured text retain a verified base plus revisions represented as unified diffs. Reconstructed content is checked before it is returned; a failed check is an error, not permission to use a lossy summary.

This is a design proposal, not a claim that the repositories already form a working memory product.

## 2. Verified Components and Boundary

### Yggdrasil Blind Storage (Java)

The Java project is a zero-third-party-dependency storage engine. It has 4 KiB authenticated pages using Ascon-128 AEAD, an integer-keyed B+Tree, slotted heap pages, a write-ahead log with redo recovery, and a Java NIO request server. Its record manager exposes insert, find, scan, and delete operations.

The TCP frame has a 14-byte header: magic byte `0x59`, opcode, 8-byte request ID, and 4-byte payload length. The standalone copy adds APPEND and bounded SCAN operations to the existing PUT, GET, DELETE, and audit operations. APPEND allocates a monotonic 32-bit key; SCAN returns key/value entries after an exclusive cursor. The request payload limit is 16 MiB.

The standalone memory server binds to loopback and still has no client authentication or TLS. Its PUT path remains insert-oriented: a duplicate key is ignored rather than replacing the existing value. The protocol does not provide namespaces or a secondary index; memory IDs and revision metadata are stored in append-only records and indexed in memory when the Rust process starts.

### `java-diff-utils-rs` (Rust)

This is a Rust port of Java diff/patch behavior, not a Java library or a storage engine. It provides Myers, linear-space Myers, and histogram diffing, patch application, and unified-diff parsing/writing. The crate forbids unsafe Rust. Its current package version is beta, and it depends on Rust crates including `regex`, `lazy_static`, `serde`, and `unicode-segmentation`.

The standalone Rust memory crate uses this library through a local path dependency and connects to Java over the versioned-by-opcode TCP frame format; there is no FFI. The combined project is **not zero-dependency**: the Rust workspace includes the diff crate dependencies and SHA-256 hashing, while the Java engine itself has no third-party runtime dependencies.

## 3. Proposed Architecture

```text
Agent / application
        |
        v
Rust Memory Layer
  - memory API and policy
  - exact/tag retrieval first
  - optional embedding-provider adapter (future)
  - diff generation, validation, and reconstruction
        |
        | versioned local TCP adapter; no direct FFI
        v
Java Yggdrasil storage engine
  - durable records and indexes
  - WAL recovery
  - authenticated encrypted pages
```

The Rust layer owns stable memory IDs and revisions. The Java engine owns durable page storage and its B+Tree. The Rust diff crate generates and applies serialized `Patch<String>` values; it does not replace the Java B+Tree or turn the Java service into a Rust binary.

For an initial local prototype, keep the adapter on loopback. Before remote use, add an authenticated transport and a versioned protocol. Do not expose the current unauthenticated server to an untrusted network.

## 4. Record and Retrieval Model

Each logical memory should carry a stable ID, revision number, namespace, content kind, fidelity class, creation and update times, access metadata, provenance, and a content hash. A revision is immutable once committed. Summaries and extracted facts are derived records linked to their source revisions; they never replace the source content.

For exact text memories, revision 1 is a full UTF-8 snapshot. Later revisions store a serialized patch generated by `java-diff-utils-rs`, plus parent and result SHA-256 hashes. Payloads are split into 3,000-byte chunks, followed by a commit marker; incomplete uncommitted chunks are ignored during recovery. On load, patches are applied in revision order and the result hash is verified before content is returned. A failed patch or hash check fails loading rather than returning questionable content.

For semantic memories, keep the original source or an explicitly accepted source representation alongside any summary. Approximate retrieval may rank candidates, but the caller should receive provenance and fidelity metadata so it can distinguish verbatim material from a summary.

### Tier Policy

- **Tier 1 — Recent / active:** retain complete records and exact snapshots for low-latency access.
- **Tier 2 — Consolidated:** retain complete semantic source plus summaries; for exact text, retain a base and validated patch chain.
- **Tier 3 — Archived / clustered:** retain provenance-linked cluster summaries and the durable source needed to restore exact memories. Tier movement must not silently destroy the only exact copy.

Promotion and demotion can use recency and access frequency. Start with a simple measured priority queue; choose a more complex heap only if benchmarks demonstrate a real benefit. Tiering thresholds, retention, and summary generation remain policy decisions, not verified behavior.

## 5. Java/Rust Integration Contract

The standalone project implements a minimal storage contract using APPEND and SCAN. APPEND returns the assigned key; SCAN accepts an exclusive 64-bit cursor and a bounded page size, and returns key/length/value tuples. Response framing, byte order, status errors, payload bounds, and request IDs are validated by the Rust client.

Each revision fragment stores its stable memory ID, revision, unique batch ID, chunk number, parent hash, and result hash in the record value. A final commit marker publishes a revision only after its chunks have been appended. The Rust layer rebuilds the memory-ID map by scanning records after restart; this is a full scan and is not yet a scalable catalog. The append sequence is not a multi-record transaction, so only committed batches are visible.

The adapter should have cross-language golden tests for frame encoding, byte order, request IDs, status codes, truncated frames, and the 16 MiB limit. It should also have restart tests proving that revisions and catalog entries remain discoverable after WAL recovery. Rust unified-diff round trips must be checked independently of storage tests.

## 6. Durability and Security Requirements

The Java page layer authenticates encrypted pages and binds authentication to page identity. This protects stored page contents against undetected tampering when pages are read through that layer; it does not by itself establish that every other data path is confidential.

Before making an end-to-end confidentiality claim, verify whether WAL records, metadata indexes, temporary files, and diagnostic output can contain plaintext. Treat data in process memory and the current TCP connection as plaintext unless separately protected. Keep the current server local-only until authentication and transport protection are added. Define key provisioning, rotation, backup, and recovery outside the page cipher implementation.

Recovery must fail closed on authentication errors, invalid patch chains, and hash mismatches. A memory result should include its source revision and whether it is verbatim, reconstructed, or summarized.

## 7. Delivery Plan and Acceptance Checks

1. **Scalable catalog:** replace startup full scans with a durable ID-to-revision index.
2. **Transactional publication:** make multi-chunk revision commits idempotent across lost responses and retry paths.
3. **Semantic path:** add summary and embedding-provider interfaces only after exact storage and provenance are stable. No provider or vector index is included here.
4. **Tier policy:** measure access patterns and storage costs; compare a simple baseline before adopting scheduling structures.

The included checks cover Java append/scan framing and Rust patch revision reloads. End-to-end validation should additionally start the local Java server, create and update a memory through the Rust CLI, restart the Java server, and verify exact retrieval. No latency, compression, or token-reduction claims are made.
